# Verified upstream runtime synchronization

The stable experimental runtime is **only** the reviewed exact lock in `contracts/runtime-bridge.lock.json`. The hourly (minute 17 UTC) or manual `Upstream HCL Runtime Sync` workflow reads public `human-cognition-layer/commits/main` metadata. Equal SHA returns `UP_TO_DATE` without installing dependencies or executing a runtime. A different SHA is a candidate, never a normal execution override. No cross-repository PAT or secret is needed.

The candidate inherits the existing interface, exact three-path allowlist, limits and experimental activation policy. Only the exact source commit/tree, file Git blob/SHA256, aggregate artifact digest, projected manifest digest and minor bridge version may change. Public requests read exact commit metadata and three exact-SHA content endpoints; no tree traversal, clone, archive, package initializer, evaluation/data material or protected source is acquired. Added research mechanisms outside this existing callable slice remain unsupported; they require a separately reviewed adapter/allowlist change. Discovery does not activate production capabilities.

`scripts/upstream_runtime_sync.py` makes a disposable copy of product files, excluding Git, dependencies and test outputs. Only this copy gets the candidate lock. Its existing fetcher downloads an external artifact, the existing worker verifies the actual callable interface and handshake, and existing discovery/smoke/Python/build/headless browser checks run against that exact pin. Original synthetic inputs and all negative and historical regressions remain unchanged. Tests compare provenance against their local exact lock, rather than a permanently hardcoded initial SHA. There is no floating-ref execution mode, bridge bypass or fallback to mock.

Every required command is bounded to five minutes; the job is bounded to 15 minutes. The receipt records `upstream_main_sha`, `candidate_sha`, `stable_verified_sha`, product source/candidate digests, individual checks, discovered capabilities, interface identity and zero provider calls/spend. Acquisition/handshake/smoke and test logs are retained in an Actions artifact for 14 days and summarized in the run. Failed candidates fail the job, remove any previous successful output and leave the stable checkout unchanged. Public API outages/rate limits remain explicit failures; the next hourly/manual run can retry without a busy retry loop. An infrastructure interruption before receipt creation remains unverified in Actions logs.

A separate publisher job receives the built-in token with product-only write permissions. Candidate tests receive no token. Before writing, `scripts/publish_runtime_sync.py` checks every acceptance result, receipt/lock/source digests, unchanged interface/policy and exact current product main SHA. It defers if main advanced or an unrelated product PR claims writer ownership. A workflow concurrency group preserves one sync writer. The deterministic branch includes candidate and product-base SHAs, so publication is idempotent and never force-updates an existing branch or resets human commits. A verified existing branch must have exactly the expected tree and sole parent. New upstream/base combinations get separate immutable review branches; older pending sync PRs are not silently rewritten or merged. Review only a current-base candidate; obsolete PRs can be closed by the reviewer.

Only the lock changes in the sync PR. Its body records previous/candidate SHA, product validation base, interface, experimental capabilities, manifest digest, tests, provider calls/spend and limitations. Ordinary execution remains on the old stable lock until adoption. The publisher explicitly dispatches the read-only `HCL Assistant Planning` workflow at the PR branch, so built-in-token event restrictions do not bypass exact-head CI. Protected required checks and reviews remain authoritative. Adoption requires merged-main exact-SHA acceptance as before.

Auto-merge is requested only when the repository permits it and main has strict required status checks including `planning`. Missing/unknown protection, disabled auto-merge, or insufficient permission leaves a review-ready PR. Settings, rulesets, paid plans and branch protection are never weakened. Current settings at implementation time: auto-merge disabled, main unprotected; automatic merge is therefore disabled. Repository administrators may enable their desired protections and auto-merge separately. A failure to publish/dispatch is an honest workflow failure, not a runtime promotion. GitHub must allow Actions to create PRs; otherwise the validated artifact remains reviewable without a new PAT.

The states mean:

| State | Role |
|---|---|
| `upstream_main_sha` | Observed branch metadata at probe time |
| `candidate_sha` | Immutable exact SHA tested in an isolated product copy |
| `stable_verified_sha` | Current reviewed lock; only pin normal HCLA experimental execution reads |

Compatibility is not efficacy. Capabilities stay `EXPERIMENTAL`, `PENDING_I06`, `production_enabled=false`; arbitrary language is never rewritten to force treatment. No confirmation/gold, protected evaluation, LongMemEval, private user data, formal-evaluation tuning or provider-backed authorization is introduced. L3 still requires I06 disposition, a production-permitted pinned artifact/interface, adapter scope validation, and explicit execution/data authorization.

Acceptance: unchanged upstream; compatible new SHA; repository/commit/blob/digest/file refusal; interface/manifest/activation drift; every failed validation stage (including smoke, regression, build/browser); stable preservation and stale-output removal; incomplete/tampered evidence refusal; concurrent writer/main refusal; lock-only publication and safe auto-merge; normal bridge rejection of a candidate. See `tests/test_upstream_runtime_sync.py` plus existing runtime provenance/lifecycle and actual synthetic/browser tests.
